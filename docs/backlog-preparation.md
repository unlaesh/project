# Подготовка бэклога к оценке — лабораторная 5, пункт 1

Скрипт `scripts/prepare_backlog.py` работает с Issues репозитория `unlaesh/project` через установленный GitHub CLI (`gh`). Python-зависимости устанавливать не требуется: используется стандартная библиотека Python 3.12+.

Каталог `scripts/backlog_catalog.json` содержит 58 описаний карточек для всех 59 конечных элементов локальной WBS. Пункты 5.1.1 и 5.1.2 покрывает одна карточка настроек уведомлений. Каталог подготовлен по текущим локальным страницам wiki и согласованным изменениям. Фактический список Issues загружается при запуске, поэтому число изменённых карточек может быть меньше 58.

## Запуск

Открой терминал в корневой папке `project`. Проверь авторизацию GitHub CLI:

```bash
gh auth status
```

Если CLI сообщает, что вход не выполнен, войди в свой аккаунт через `gh auth login`.

**1. Сформируй план и резервную копию. Эта команда ничего не меняет на GitHub:**

```bash
python3 scripts/prepare_backlog.py plan
```

Скрипт выведет пути к `plan.json` и `report.md`. В отчёте указаны конкретные номера Issues, проблемы сопоставления и различия между старым и предложенным текстом. Полные новые тексты находятся в соседней папке `proposed/`.

**2. После просмотра отчёта примени именно сохранённый план:**

```bash
python3 scripts/prepare_backlog.py apply
```

По умолчанию используется последний план. Можно явно указать путь:

```bash
python3 scripts/prepare_backlog.py apply .backlog-preparation/ИМЯ_ЗАПУСКА/plan.json
```

При временном сетевом сбое повтори `apply` для того же плана: скрипт сверит фактические тексты и не будет повторять уже выполненные изменения. Если карточка изменилась после формирования плана, её изменение будет пропущено с объяснением; для неё нужен новый `plan`.

После применения прочитай `apply-results.json`: там отражены результаты операций и оставшиеся вопросы. Запуск не означает, что все вопросы закрыты: `review`, `conflict`, `missing` и незаданные параметры оценки требуют отдельного разбора.

## Что изменяется

- Заголовки, описания, критерии готовности и границы однозначно сопоставленных открытых задач.
- Одна существующая карточка 5.1.1 расширяется на 5.1.1 и 5.1.2. Если обнаружатся две отдельные карточки, скрипт отметит конфликт и сохранит их.
- Стандартные разделы заменяются согласованными версиями из каталога. Дополнительные разделы, например «Решения команды», и явно записанные зависимости сохраняются. Все исходные тексты остаются в резервной копии и видны в diff отчёта.

Номера Issues, комментарии, исполнители, метки, состояния, milestones и поля GitHub Project сохраняются. Закрытые задачи и задачи с выполненными пунктами автоматически не переписываются. Скрипт не меняет wiki, не создаёт коммиты, не отправляет сообщения участникам, не выставляет оценки и календарные даты.

## Сопоставление и полнота

Карточка определяется по явной строке «Элемент WBS» / «Элементы WBS» в начале описания или коду WBS в начале заголовка. Упоминание чужой задачи в зависимости или критериях не считается идентификатором этой карточки. Конфликт заголовка и описания, повторяющиеся карточки и неизвестные коды выводятся в отчёт.

Отсутствие карточки с распознанным кодом ещё не доказывает, что работа потеряна: она может находиться в задаче без кода или быть объединена с другой. Поэтому создание новых Issues по умолчанию отключено. Если после просмотра отчёта отсутствие подтверждено, можно сформировать новый план с созданием пропущенных работ:

```bash
python3 scripts/prepare_backlog.py plan --create-missing
python3 scripts/prepare_backlog.py apply
```

Создание блокируется при неразобранных неоднозначных карточках. Скрипт ещё раз проверяет существующие Issues перед созданием. Новые карточки получат только заголовок и описание; их приоритет и включение в GitHub Project нужно проверить отдельно. Если авто-добавление в Project, описанное в Development, настроено, оно может выполнить добавление.

## Восстановление

Каждый запуск `plan` сохраняет исходный список Issues, исходные и новые тексты, план и отчёт в `.backlog-preparation/`. Эта папка исключена из Git; сохраняй её до завершения работы.

Вернуть прежние заголовки и описания изменённых карточек последнего плана:

```bash
python3 scripts/prepare_backlog.py restore
```

Для более раннего плана укажи путь к его `plan.json`. Восстановление пропускает карточки с более поздними изменениями; созданные Issues не удаляются. Проверка перед записью уменьшает риск перезаписи одновременной правки, но не является блокировкой GitHub: во время `apply` лучше не редактировать те же карточки параллельно.

## Границы и исходные данные

- 2.1.2 проектирует полную модель данных; 2.2.3 реализует её часть для MVP; 4.1.1 добавляет заметки отдельной миграцией; данные уведомлений добавляются в блоке 5.
- 3.4.4 формирует общий текст расписания; получение данных и навигация находятся в 3.4.1–3.4.3, вывод заметок — в 4.2.3.
- Для повторяющихся управленческих работ 1.3.1 и 1.3.2 параметры определены на период 12.11–15.12.2026: пять итераций и 24 ежедневные сверки для пяти участников (35 чел.-ч), три контрольные проверки Дениса и Алины (4 чел.-ч). Это плановые нормативы учебной модели, а не проведённые встречи или фактическая доступность команды. Подробный расчёт — в локальной wiki, на странице Development. Эти часы учитываются внутри доступного времени участников, без повторного включения в технические задачи.
- Локальная wiki согласована с каталогом: NFR-3 допускает ограниченные повторы; NFR-16.1 проверяет регистрацию до MVP, а заметки после их реализации; NFR-2 измеряет задержку успешной отправки через Telegram Bot API. Изменения wiki коммитятся и отправляются из отдельного репозитория `project.wiki`.

### Ручной перенос параметров задач #8 и #9

Готовые описания сохранены в [issue-8.md](issues/issue-8.md) и [issue-9.md](issues/issue-9.md). Содержимое каждого файла целиком предназначено для поля описания соответствующей существующей карточки; заголовок, статус, исполнители и прочие поля меняются отдельно только при необходимости. Эти же формулировки находятся в каталоге. Подготовка файлов выполняется локально и сама по себе не обновляет Issues на GitHub.

После ручного переноса параметров #8 и #9 все выявленные вопросы к конкретности описаний из первого пункта лабораторной устранены. Поля Estimate, группировка по майлстоунам и календарные сроки технических работ относятся к следующим пунктам. Наличие плана управленческих событий не означает, что все функции продукта уже помещаются в срок 15 декабря: это проверяется после оценки трудоёмкости, зависимостей и доступного времени.

## Проверка без GitHub

Проверка полноты каталога по локальной WBS:

```bash
python3 scripts/prepare_backlog.py validate
```

Автоматические тесты используют имитацию GitHub и не обращаются в сеть:

```bash
python3 -m pytest tests/test_prepare_backlog.py -q
```

Для анализа заранее полученной выгрузки REST API можно выполнить `plan --from-json PATH`. Это офлайн-план, его применение запрещено: для записи сначала сформируй свежий `plan` непосредственно с GitHub.

## Перед коммитом

Перед коммитом выполняются проверка покрытия WBS, линтер, проверка форматирования и тесты. Повторить проверки в окружении разработки с зависимостями проекта можно так:

```bash
ruff format scripts/prepare_backlog.py tests/test_prepare_backlog.py
ruff check .
ruff format --check .
pytest
```

Если пакет проекта ещё не установлен, тесты можно запустить из корня через `PYTHONPATH=src python3 -m pytest -q`. Для обычной разработки используй установку зависимостей из README.
